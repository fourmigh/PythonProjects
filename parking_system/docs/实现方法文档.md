## 2. 数据结构选择

| 数据 | 实现 | 位置 | 设计意图 |
|---|---|---|---|
| 用户 | `User` dataclass | models.py:15 | id、slots、spot_assigned、checked_in/out、checkin/checkout_time、overtime、overtime_start、actual_end_slot |
| 预订计数 | `occupied = [0]*num_slots` 列表 | parking_system.py:50 | 每时段预订总量；预订 +1，到达成功 -1（转实际占用） |
| 车位日程 | `spot_schedule = defaultdict(dict)` | parking_system.py:53 | `{车位: {时段0基: user_id}}`，到达后才写入 |
| 车位位图 | `spot_bitmap: dict[车位, int]` | parking_system.py:54 | 缓存车位占用位图，冲突检测 O(1) |
| 时段状态 | `TimeSlotStatus` dataclass | models.py:30 | booked_count / actual_count / capacity / is_past |

### 位图核心（core/utils.py）

```python
bitmap = ((1 << (end - start + 1)) - 1) << start   # 第 i 位 =1 表示时段 i 被占用
```

- 两订单冲突 = `bitmap_a & bitmap_b != 0`；
- `has_overlap` 用首尾比较。

注意：`_update_spot_bitmap`（parking_system.py:67、allocation.py:23）生成车位位图
用的是 `1 << (slot + 1)`（从第 slot+1 位起），与 `calculate_bitmap` 的编码（从第 start 位起）**不一致**，见 §6 疑点 1。

## 3. 各需求的实现方法

### 3.1 预订 book（parking_system.py:108）

1. 校验 slots 相邻连续；
2. 校验所有时段 `> time_point // 2`（未过去）；
3. `_check_slots_availability`（parking_system.py:73）：
   - 逐时段检查 `occupied[idx] < total_spots`；
   - 求多时段的"同时空闲车位集合"（对每时段扫全部车位构建占用集合再求交集），
     有交集 → 可用并返回该集合；
   - 无交集 → 计算每车位冲突数，取冲突最少的 5 个作为推荐，返回失败；
4. 成功：`occupied[每时段] += 1`，登记 `User(id, slots)`。
   记录不绑车位 —— 具体车位延迟到 arrive 分配。

### 3.2 简单到达 arrive（parking_system.py:134）

1. 状态机校验（存在/未到达/未离开/到达时段正确）；
2. 扫描全部用户构建 `occupied_spots`（在场且非离场的已分配车位集合）；
3. `free_spots` = 全车位 - occupied_spots；
4. 为每个空位调用 `allocation_manager._can_fulfill_future_users`，
   取第一个通过者；全部不通过则失败"没有合适的车位"；
5. 成功后：写 `spot_schedule`、刷新车位位图、`occupied` 计数 -1。

### 3.3 智能到达 arrive_smart（parking_system.py:194）

与 arrive 相同的状态校验与空位计算后：

1. 候选车位 = 前 `MAX_CANDIDATE_SPOTS(50)` 个空位（空位太多时截断）；
2. 调 `AllocationManager.allocate_smart`；失败则用全部空位再试一次，再失败返回错误；
3. 同样写入 spot_schedule / 位图 / occupied -1。

### 3.4 智能分配核心 AllocationManager.allocate_smart（allocation.py:176）

流程：

1. `_get_future_bitmaps_optimized`（allocation.py:250）：收集满足下列条件的未来订单
   位图 —— 未到场未离场、首时段 `> current_time+2`、与当前用户时段
   （若 `CONSIDER_OVERTIME` 则尾部扩展 `OVERTIME_EXTEND_SLOTS=1` 段）有重叠；
   上限 `MAX_FUTURE_ORDERS=10`。
2. 逐候选车位：
   - 该车位位图与任何未来位图冲突 → 跳过；
   - `_can_fulfill_future_users`（allocation.py:61）→ 不通过则跳过；
   - `_calculate_spot_score` 打分，保留最高分（同分取小编号车位）。
3. 三级降级：
   - 第一轮失败 → 重扫但跳过"未来用户可满足"检查；
   - 仍失败 → 直接取 `free_spots[0]`；
   - 无任何空位 → 返回失败。

### 3.5 打分函数 _calculate_spot_score（allocation.py:109）

全部权重在 config.py `AllocationWeights`：

| 维度 | 规则 | 分值 |
|---|---|---|
| 连续性 | 左右两侧（相邻车位）在本用户时段内均空闲 =50；单侧空闲 =20 | 50/20 |
| 到达紧迫性 | `urgency = 首时段 - time_slot - 1`，0/1/2 分别 +100/+50/+20 | 100/50/20 |
| 时长匹配-长停 | `时长 >= 0.7*num_slots`：数车位在用户结束后的连续空段（≤8 段），30 + 1/段 | 30+ |
| 时长匹配-短停 | `时长 ≤ 2` 且车位为角落（1 号或最末号）+30 | 30 |
| 当前空闲 | 车位位图与用户位图完全无冲突 +30 | 30 |
| 超时风险 | 延展段已被占 -30 | -30 |

### 3.6 未来用户保护 _can_fulfill_future_users（allocation.py:61）

快速通道：`FAST_CHECK_MODE` 开启且剩余空位 ≥ 5 → 直接通过。

否则贪心模拟：

1. 按 `CHECK_ONLY_CONFLICTING_FUTURE_USERS` 开关选择：
   只检测与当前用户时段重叠的未来用户，或全部未来用户；
   排序后截断至 `MAX_FUTURE_USERS_CHECK=15`；
2. 在临时位图副本上把当前用户"假装"分配到候选车位；
3. 为每个未来用户按车位编号顺序找第一个位图不冲突的空位，找不到 → 返回 False；
4. 找到则把该订单位图合并进临时位图并继续（无回溯）。

### 3.7 离场与超时 depart（parking_system.py:657）

- 已处于 overtime 状态的用户：直接标记 checked_out，清理预订时段及
  `[slots[-1]+1, actual_end_slot]` 超时时段的 spot_schedule 记录，更新位图；
- 未超时但 `overtime=True` 调用（续停）：`actual_end_slot + 1`，
  将新超时时段写入该车位 spot_schedule；
- 正常离场：要求 `time_slot + 1 == slots[-1]`，清理预订时段记录。

### 3.8 诊断子系统（parking_system.py:270-654）

- `_analyze_no_free_spots`：打印分隔线报告 —— 车位占用详情（含超时用户实际占用范围）、
  超时/正常用户清单、当前时段超时占用、各时段预订满况、已满时段的占用者列表；
- `_recommend_spots_for_user`：为每个车位算未来订单冲突与占用者冲突，
  输出四类统计（理想 / 空闲但未来冲突 / 被占不冲突 / 被占且冲突）、
  超时占用车位明细和瓶颈结论。
- 大量依赖 `hasattr(user, 'actual_end_slot')` 判空（dataclass 字段本已存在）。

### 3.9 时间与状态查询

- `advance_time`（parking_system.py:721）：直接赋值 `self.time_point`；
- `get_slot_status`（parking_system.py:725）：`actual` 逐用户遍历累加——在预订时段内，
  或超时且在 `(slots[-1], actual_end_slot]` 内，或已离场但在
  `[checkin+1, checkout+1]` 区间内各 +1；`booked_count` 取 `occupied` 数组。

### 3.10 性能统计

类级 `_perf_stats` defaultdict + `_profile` 装饰器（基于 `time.time()`），
覆盖 book / arrive / arrive_smart / depart / advance_time / get_slot_status 等，
`print_perf_stats()` 输出调用次数、总耗时、平均毫秒。

### 3.11 UI 实现

- `ParkingSystemProxy`（ui/system_proxy.py:15）：`__new__` 单例；注册/注销刷新回调；
  `_notify_refresh()` 通知所有窗口；属性直通底层 system（含暴露 users / spot_schedule
  等可变对象引用）。
- 主窗口（ui/parkinggui.py）：Canvas/Frame 渲染时段热力条（颜色映射空闲/紧张/已满/已过去），
  `on_slot_click` 选择区间，预订面板提交 `proxy.book` / `proxy.arrive[_smart]`；
  `reset_system` 支持运行时改车位数与时段数并 `rebuild_ui`。
- 车位状态窗口（ui/spot_status_window.py）：车位网格 + 点开详情；
  `advance_time` / `auto_advance_step`（after 定时器）推进时间；
  时间推进时调 `process_time_start/End` 检测到点与离点、
  `process_all_overtime_users` 批量处理超时；`force_depart_user` 强制离场。

### 3.12 测试脚本

`ParkingSystemAdvancedTester`：生成非重叠/随机时段组合；
`random_test`（万级次数）、`stress_test`、`edge_case_test`（含 overtime 决策模式）；
对 arrive 与 arrive_smart 分别对比成功率/失败案例/耗时；
`calculate_combinatorial_explosion` 用于说明为什么用启发式而非穷举。

## 4. 复杂度与扩展性概况

- 预订可用性检查：O(slots × spots)（逐时段扫全车位，未用位图）；
- 到达空位计算：O(users) + O(spots)；
- allocate_smart：O(候选车位 × 未来订单数) 位图与运算为主，
  上界受 MAX_CANDIDATE_SPOTS=50、MAX_FUTURE_ORDERS=10、MAX_FUTURE_USERS_CHECK=15 截断；
- _can_fulfill_future_users 最坏：15 用户 × slots 车位 × 位图交集；
- 诊断函数：O(spots × users)，仅在失败路径执行。

## 5. 设计上的可选替代方案（供评估对比）

- 预订即绑定车位（预约式）vs 当前延迟分配 —— 两者权衡预订成功率 vs 到达分配自由度；
- 未来用户保护的反向 greedy（无回溯）vs 二分匹配（Hopcroft–Karp）/回溯 —— 当前实现可能误拒；
- 区间树 / 每时段 bitset 数组 vs 当前单 int 位图 —— 2*num_slots 位内单 int 足够；
- 诊断日志与业务类分离为独立 DiagnosticAnalyser 以降低 ParkingSystem 体量
  （当前单文件 758 行，近半是诊断文本拼接）。

## 6. 疑点与疑似缺陷清单（重点评估对象）

1. **位图编码不一致（疑似 bug）**：
   `calculate_bitmap`（从第 `start` 位起）与 `_update_spot_bitmap`（从第 `slot+1` 位起，
   0 位恒空）编码错位 1 位。`allocate_smart` 中 `spot_bitmap（后者编码） & future_bitmaps（前者编码）`
   的"快速冲突检查"（allocation.py:197-200）可能时段错位而误判/漏判冲突。
2. **`AllocationManager` 的 time_point 快照问题**：只在首次 `_init_allocation_manager`
   时以构造参数固化 `time_point`（parking_system.py:58-65），此后 `advance_time`
   推进时间不会更新该快照，影响 `_get_future_users` 等基于当前时间的判断。
3. **`occupied` 计数语义**：预订 +1 / 到达 -1，实际含义是"已预订未到场"数；
   但 `_check_slots_availability` 用它判断"时段已满"，
   与"满"应为 超时在场 + 未来的预订总量 之和的语义可能不符（尤其有超时用户时）。
4. **depart 的 overtime 分支顺序**：顶部 `if user.overtime` 先 return，
   中段的 `if overtime:` 续停块只对"尚未处于超时态"的用户执行；
   且正常离场校验 `time_slot + 1 == slots[-1]` —— 超时用户如何走到正常离场分支的路径较绕。
5. **get_slot_status 的 booked_count**：到达后占用计数被 -1，
   已超时脱管的用户也不再计入，与"预订数"直观语义可能不一致（需对照需求口径）。
6. **死代码 / 冗余**：`FUTURE_CONFLICT_PENALTY=1000`、`MAX_CHECK_SLOTS` 部分配置、
   `UserStatus` 枚举（models.py:7）未使用；`_recommend_spots_for_user` 与
   `_get_future_bitmaps_optimized` 逻辑重复；`hasattr` 判断 dataclass 固有字段多余；
   简版 `book`/`_check_slots_availability` 未利用位缓存重复 O(spots×slots) 扫描。
7. **打分函数中 `spot_bitmap >> slot`**：以"第 slot 位"读状态，
   但车位位图生成是 `slot+1` 位 —— 与疑点 1 同源。
8. **`_can_fulfill_future_users` 与 `arrive_simple` 的一致性**：简单策略也依赖
   同一保护检查，但 `arrive` 未经过位图冲突预检，可能在"已预订未来时段的车位"上
   把车放进去（而该时段已被人远程预订）—— 需要评估这是否为合法/期望行为。

## 7. 给评估 AI 的核对问题

- 疑点 1 的位图错位是否成立？修正为统一编码后，冲突检测是否完备？
- 延迟分配模型（book 不锁车位）在"超时挤占 + 未来保护"下是否会造成首时段到达高峰的失败率异常？
- `_can_fulfill_future_users` 应否换成区间匹配/二分图匹配以减少误拒？
- 三级降级（放弃未来保护 → 任意空位）是否违背需求 2.4 的硬约束？其失效路径应否显式提示？
- 打分权重（紧迫性 100 > 连续性 50）与真实车库语义（紧凑停车）是否匹配？
- `occupied` 数组是否应重构为"预订口径"与"在场口径"两套独立累计？
