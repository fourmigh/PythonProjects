## 2. 数据结构选择

| 数据 | 实现 | 位置 | 设计意图 |
|---|---|---|---|
| 用户 | `User` dataclass | models.py:15 | id、slots、spot_assigned、checked_in/out、checkin/checkout_time、overtime、overtime_start、actual_end_slot |
| 预订计数 | `occupied = [0]*num_slots` 列表 | parking_system.py:50 | 每时段预订总数（含已到场用户）；仅预订 +1，到达/离开都不减少，维持「每时段预订数 ≤ 总车位数」不变量 |
| 车位日程 | `spot_schedule = defaultdict(dict)` | parking_system.py:53 | `{车位: {时段0基: user_id}}`，到达后才写入 |
| 车位位图 | `spot_bitmap: dict[车位, int]` | parking_system.py:54 | 缓存车位占用位图，冲突检测 O(1) |
| 时段状态 | `TimeSlotStatus` dataclass | models.py:30 | booked_count / actual_count / capacity / is_past |

### 位图核心（core/utils.py）

```python
bitmap = ((1 << (end - start + 1)) - 1) << start   # 第 i 位 =1 表示时段 i 被占用
```

- 两订单冲突 = `bitmap_a & bitmap_b != 0`；
- `has_overlap` 用首尾比较。

`_update_spot_bitmap`（parking_system.py）读取的是 `spot_schedule`
的 0 基时段 key，`1 << (slot + 1)` 恰好落在「1 基时段号」上，与
`calculate_bitmap` 的 `<< start` 编码一致（早期文档记录的「错位 1 位」经复核不成立）。

## 3. 各需求的实现方法

### 3.1 预订 book（parking_system.py:108）

1. 校验 slots 相邻连续；
2. 校验所有时段 `> time_point // 2`（未过去）；
3. `_check_slots_availability`（parking_system.py:73）：
   - 逐时段检查 `occupied[idx] < total_spots`；
   - 求多时段的"同时空闲车位集合"（对每时段扫全部车位构建占用集合再求交集），
     有交集 → 可用并返回该集合；
   - 无交集 → 计算每车位冲突数，取冲突最少的 5 个作为推荐，返回失败；
4. 成功：`occupied[每时段] += 1`，登记 `User(id, slots)`。
   记录不绑车位 —— 具体车位延迟到 arrive 分配。

### 3.2 到达分配 arrive（parking_system.py）

唯一入口。流程：

1. 状态机校验（存在/未到达/未离开/到达时段正确）；
2. `user_bitmap = calculate_bitmap(user.slots)`；
3. `_find_conflict_free_spot`：随机选起点，环形扫描全部车位，
   返回第一个 `spot_bitmap[spot] & user_bitmap == 0` 的车位；
4. 找不到 → 调 `_analyze_no_free_spots` 输出失败诊断；找到 → 写
   `spot_schedule`、刷新车位位图。

**不遍历任何订单**。依据：用户严格按 `slots[0]` 顺序到场，任何与当前用户
时段重叠的已分配用户必然覆盖当前用户的起始时段，因此剩余可用车位数
只取决于「总车位数 − 起始时段同时在场人数」，与历史选位方式无关。只要
`book` 保证每时段预订总数 ≤ 总车位数，任选无冲突车位都不会让后续预订
用户无处可停。这一结论对随机选位同样成立，不需要 First-Fit，更不需要
订单模拟。

### 3.3 离场与超时 depart（parking_system.py:657）

- 已处于 overtime 状态的用户：直接标记 checked_out，清理预订时段及
  `[slots[-1]+1, actual_end_slot]` 超时时段的 spot_schedule 记录，更新位图；
- 未超时但 `overtime=True` 调用（续停）：`actual_end_slot + 1`，
  将新超时时段写入该车位 spot_schedule；
- 正常离场：要求 `time_slot + 1 == slots[-1]`，清理预订时段记录。

### 3.4 诊断子系统（parking_system.py）

- `_analyze_no_free_spots`：打印分隔线报告 —— 车位占用详情（含超时用户实际占用范围）、
  超时/正常用户清单、当前时段超时占用、各时段预订满况、已满时段的占用者列表；
- `_recommend_spots_for_user`：为每个车位算未来订单冲突与占用者冲突，
  输出四类统计（理想 / 空闲但未来冲突 / 被占不冲突 / 被占且冲突）、
  超时占用车位明细和瓶颈结论。
- 大量依赖 `hasattr(user, 'actual_end_slot')` 判空（dataclass 字段本已存在）。
- 这些函数只在 `arrive` 真实失败时执行，遍历用户生成报告，不影响正常分配路径性能。

### 3.5 时间与状态查询

- `advance_time`：直接赋值 `self.time_point`；
- `get_slot_status`：`actual` 逐用户遍历累加——在预订时段内，
  或超时且在 `(slots[-1], actual_end_slot]` 内，或已离场但在
  `[checkin+1, checkout+1]` 区间内各 +1；`booked_count` 取 `occupied` 数组
  （该时段的预订总数）。

### 3.6 性能统计

类级 `_perf_stats` defaultdict + `_profile` 装饰器（基于 `time.time()`），
覆盖 book / arrive / depart / advance_time / get_slot_status 等，
`print_perf_stats()` 输出调用次数、总耗时、平均毫秒。

### 3.7 UI 实现

- `ParkingSystemProxy`（ui/system_proxy.py:15）：`__new__` 单例；注册/注销刷新回调；
  `_notify_refresh()` 通知所有窗口；属性直通底层 system（含暴露 users / spot_schedule
  等可变对象引用）。
- 主窗口（ui/parkinggui.py）：Canvas/Frame 渲染时段热力条（颜色映射空闲/紧张/已满/已过去），
  `on_slot_click` 选择区间，预订面板提交 `proxy.book` / `proxy.arrive`；
  `reset_system` 支持运行时改车位数与时段数并 `rebuild_ui`。
- 车位状态窗口（ui/spot_status_window.py）：车位网格 + 点开详情；
  `advance_time` / `auto_advance_step`（after 定时器）推进时间；
  时间推进时调 `process_time_start/End` 检测到点与离点、
  `process_all_overtime_users` 批量处理超时；`force_depart_user` 强制离场。

### 3.8 测试脚本

`ParkingSystemAdvancedTester`：生成非重叠/随机时段组合；
`random_test`（万级次数）、`stress_test`、`edge_case_test`（含 overtime 决策模式）；
统计到达成功率、失败案例与耗时；
`calculate_combinatorial_explosion` 用于说明为什么用启发式而非穷举。

## 4. 复杂度与扩展性概况

- 预订可用性检查：O(slots × spots)（逐时段扫全车位，未用位图）；
- 到达分配：O(spots) 次整数与运算（随机起点环形扫描，命中即返回），
  不遍历用户、不遍历订单；
- 失败诊断：O(spots × users)，仅在真实失败路径执行。

## 5. 设计上的可选替代方案（供评估对比）

- 预订即绑定车位（预约式）vs 当前延迟分配 —— 两者权衡预订成功率 vs 到达分配自由度；
- 随机起点扫描 vs 固定最小号 First-Fit —— 前者分散车位磨损，后者低号更集中；
  在「按开始时段到达 + 每时段预订数 ≤ N」前提下两者都不会失败；
- 区间树 / 每时段 bitset 数组 vs 当前单 int 位图 —— 2*num_slots 位内单 int 足够；
- 诊断日志与业务类分离为独立 DiagnosticAnalyser 以降低 ParkingSystem 体量。

## 7. 给评估 AI 的核对问题

- 超时续停突破「每时段预订数 ≤ N」时，是否应预留缓冲车位（book 上限改为 N - buffer）？
- 随机起点扫描牺牲了「相邻车位紧凑停放」的观感，是否需要在可用车位中重新引入连续性排序？
- `book` 的 `common_free`（所有时段的共同空闲车位交集）比「每时段预订数 ≤ N」更保守，
  是否会误拒本可分配的预订？是否应改为区间图着色可行性判断？
- `occupied` 只增不减：未到场用户会一直占用容量。是否需要「未到场自动释放」策略？
