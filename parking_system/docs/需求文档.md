# 停车场（自行车停车库）预订系统 —— 需求文档

> 本文档从现有代码反推整理，只描述**领域需求**（用户可感知的功能与业务规则），
> 不涉及具体实现方式（如分配时机、数据结构、算法选型——这些移入《实现方法文档》
> 或列为开放设计决策点）。
> 来源：`README.md`、`core/`、`ui/`、`test_parking_system.py` 全量代码分析。

---

## 1. 项目定位

一个停车场 / 自行车停车库的**时段预订管理系统**（模拟系统）。

系统模拟一个停车库的完整运营：用户提前预订某段时间 → 到来时取得一个车位 →
在预订时间内停车（可能超时）→ 取车离开。管理方（或系统）须能随时掌握
各时段与各车位的占用情况。

## 2. 领域概念

### 2.1 车位

- 车库拥有固定数量的车位（`total_spots`），车位可按编号区分；
- **每个车位同一时间只能被一辆车占用**（车位的物理硬约束）。

### 2.2 时段与时间

- 一天划分为多个等长时段（如 24 个时段，每个时段 1 小时；时段数可配置）；
- 时段编号从 1 开始，一天结束时消耗完；
- 存在一个**模拟当前时间**，随系统运行（手动或自动）向前推进；
- 已过去的时间段不可再被预订或分配。

### 2.3 用户与订单

- 用户是预订的发起者，须可识别（有编号）；
- 一个订单 = 一位用户 + 一段**连续**时段 + 最终落在一个具体车位上；
- 一次预订占用的时段必须连续，不能跳跃或分散。

## 3. 功能需求

### 3.1 预订

用户应能提前为自己预订一段未来的连续时段，须满足：

1. **时间合法性**：预订的任意时段不得早于当前时间；
2. **连续性**：所订时段必须连续；
3. **容量约束**：所订的每个时段都不能超出车库对该时段所能提供的总容量
   （总容量 = 车位数；某时段的"满"包括该时段未来会被或正在被占用的全部情形）；
4. 预订失败时，系统须给出人读的失败原因；
5. 预订成功后，该用户所订时段的容量权益应受到保护，
   其他用户的任何安排不得使其预订失效（见 3.2 的约束）。

> 注：需求只约定"预订发生后容量权益受保护"，**不约定预订时是否锁定具体车位**
> ——这是留给实现的开放决策点（见 §5）。

### 3.2 车位分配

当用户需要（按预订到来或按规定时刻到来）使用车位时，系统须为其安排一个具体车位：

1. 一次分配应覆盖该用户订单的全部时段，且满足其连续性；
2. **公平/保护约束**：分配不得损害其他已预订用户的权益——
   完成本次分配后，所有已预订用户在各自预订时段内仍应有机会取得车位；
3. 当存在多个可行车位时，系统**可以**依据某种偏好做出选择
   （如紧凑停放、利于后续停车等偏好——具体策略见 §5 开放决策点）；
4. 分配失败时，系统须给出人读的失败原因，并**应尽可能解释失败的结构性原因**
   （哪些时段已满、哪些车位被谁/超时占用、与其他预订如何冲突等），
   以便诊断与调整；
5. 到来时刻不合规（早到/晚到不在可接受窗口内）、用户重复到达、
   用户不存在等异常到达，系统应识别并拒绝。

### 3.3 停车（占用期间）

1. 用户在停车期间持续占用其被分配的车位，他人不得使用该车位；
2. **超时**：若用户在预订时段结束后仍未离开，即构成超时：
   - 系统须能识别超时用户，并在后续时段将其计入实际占用（挤占容量）；
   - 一般情况下超时用户**不换车位**，在原位继续停放；
   - 超时的用户应可被管理方查询、催离或强制离场。

### 3.4 取车（离场）

1. 用户取车离开后，其车位即归还，后续时间段可重新分配给他人；
2. 超时用户离场时，其超时占用的时间段也一并结清归还；
3. 离场时间不合规（不存在对应订单、重复离开、离开时刻异常）
   系统应识别并拒绝。

### 3.5 时间推进

1. 系统支持（手动和自动）推进模拟时间；
2. 时间推进后：过去时段不可再预订/会被判定过去；到场或超时状态随之变化；
3. 可/reset 重置系统回到初始状态重新模拟。

### 3.6 查询与可视化

系统须能回答以下运营查询：

1. **时段维度**：任一时段的——
   - 预订数量（尚未到场、已订未来时段的合计）；
   - 实际在场数量（含超时用户在超时时段的占用）；
   - 容量与是否已过去；
2. **车位维度**：任一车位当前被谁占用、占用到什么时候、是否超时；
3. **用户维度**：任一用户的订单、到场状态、是否超时。

界面（Tkinter，模拟管理台）应呈现：

- 主窗口：按时段展示占用状况，点击选择连续区间进行预订，
  显示当前模拟时间，支持运行时重置（车位数、时段数可改）；
- 车位状态窗口：车位网格 + 每车位占用详情、等待中与超时用户列表、
  推进时间（手动/自动）、批量处理超时用户、单个强制离场。

## 4. 非功能性需求 / 约束

1. **零依赖**：仅 Python 标准库（含 tkinter），Python 3.10+；
2. **性能**：须能在压力测试场景（高用户数、大量随机预订与到达）下保持可用响应速度，
   冲突判定须高效（结果性要求，具体手段由实现选择）；
3. **可调优**：分配相关的策略参数（权重/阈值/开关）应集中配置、可无侵入调优；
4. **可测试**：核心业务逻辑与界面完全解耦，可独立驱动测试；
5. **可解释性**：失败与诊断信息面向人阅读（用于调参和定位瓶颈）。

## 5. 留给设计 / 评估的开放决策点

以下问题**需求不规定**，由实现自行选择；评估时应对照《实现方法文档》判断其取舍：

1. **分配时机**：预订时就锁定具体车位（预约式），还是预订只登记权益、
   到来时才分配（延迟分配）？
   —— 权衡：预订成功率、到达高峰的分配自由度、超时挤占的处理复杂度。
2. **分配策略**：首个可行车位，或多因子打分选最优（紧凑度/紧迫性/超时风险等）？
3. **未来用户保护程度**：每次分配都严格保证未来预订可满足（硬约束），
   还是检测到困难时降级、先保当前用户（软约束 + 降级路径）？
4. **超时规则**：是否允许无限续停、是否对超时占用的时段收费/处罚、
   超时是否可被强制换位。
5. **保护性检查的完备性**：采用简单贪心模拟，还是二分图匹配等更完备的算法，
   以避免把"本可安排"的情形误判为不可行。

## 6. 测试需求（验收方式期望）

- 随机测试：随机生成预订/到达/离场序列，检验功能正确性并给出统计；
- 压力测试：高用户数高强度操作，检验性能与失败率走势；
- 边界测试：极端场景（车位数极少、用户全超时、临界时段等）；
- **策略对比**：能对比不同分配策略（如"简单 vs 智能"）的成功率与耗时，
  以支持评估与调参；
- **诊断输出**：对失败的案例能还原现场（车位占用、超时情况、冲突时段、推荐结论）。
- 性能统计：核心操作调用次数与平均耗时可见，用于性能回归。
